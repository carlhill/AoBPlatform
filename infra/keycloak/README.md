# Keycloak (identity)

`realm-export.json` is imported automatically when the `keycloak` container
starts (`start-dev --import-realm`) — realm `aobplatform` on
http://localhost:21024, admin console admin/admin (local dev only).

The export is GENERATED by `transform-realm.mjs` from ReferralPlatform's
proven realm (WebAuthn policies, flow shapes) — edit the transform and re-run
it rather than hand-editing 40KB of JSON:

```bash
node infra/keycloak/transform-realm.mjs
```

## What's in the realm

- **Realm roles**: `provider`, `practice_principal`, `practice_manager`,
  `front_desk`, `patient`, `assignor`, `system`.
- **Public client `web`** (console/portal/tester) — authorization code + PKCE,
  bound via `authenticationFlowBindingOverrides` to the **`clinician-browser`
  flow, where a WebAuthn passkey is REQUIRED with no password/OTP fallback**.
  That is rule 15 (REQ-VAULT-04) enforced at the identity layer: practitioner
  and admin auth is passkeys, no password-only paths.
- **`patient-carer-browser` flow** (passkey as ALTERNATIVE to password+OTP —
  encouraged, not mandatory) — ready for the patient/assignor portal client
  when M8 auth lands (REQ-CLIENT-02: passkey never a barrier for patients).
- **Confidential service clients** `core-service`, `rules-service`,
  `vault-service` — client-credentials only, used by
  `@aobplatform/auth-client`'s `ServiceTokenProvider` (core already requests
  real tokens for vault calls when `KEYCLOAK_ISSUER`/`KEYCLOAK_CLIENT_SECRET`
  are set).
- **No social/broker identity providers** — deliberately absent given the
  AoB phishing exposure; adding one is a decision, not a default.

## Verified (21 Aug 2026)

Realm imports and boots; OIDC discovery serves; `core-service` obtains a real
client-credentials token; `@aobplatform/auth-client`'s `TokenVerifier`
verifies it against the realm JWKS end to end.

## Staged next (not yet wired)

- Inbound auth guards on core/rules/vault verifying bearer tokens (the
  enforcement half — lands with the login surfaces so the console isn't
  locked out before it can log in), replacing the `x-practice-id` dev header
  with the token's `practice_id` claim.
- Practitioner enrolment ceremony + passkey registration UX (REQ-PKI-01).
- Patient/assignor portal client + the three-identifier bootstrap (FR-8.2).

Issuer note (ReferralPlatform lesson): tokens carry the PUBLIC issuer
(`http://localhost:21024/...`) regardless of which host the request hit —
containers must validate against that while fetching JWKS via their internal
route (`TokenVerifier`'s `jwksUri` override exists for exactly this).
