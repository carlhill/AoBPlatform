# Keycloak (identity)

`realm-export.json` is imported automatically when the `keycloak` container
starts (`start-dev --import-realm`) — realm `aobplatform` on
http://localhost:21024, admin console admin/admin (local dev only).

The export was GENERATED by `transform-realm.mjs` from ReferralPlatform's
proven realm (WebAuthn policies, flow shapes).

**⚠ It is no longer safe to re-run that script (found 12 Sep 2026).** The
committed export has moved on from what the transform produces, and some of the
drift is safety-critical: the export has
`webAuthnPolicyUserVerificationRequirement: required` where the transform still
says `preferred`, and both RpIds pinned to `localhost` where the transform
leaves them blank — the two fixes from §2 below. It also predates
`platform_admin` and the `console` client. Regenerating today silently reverts
all of that. Hand-edit the export for small changes until the drift is
reconciled (TODO.md), and keep the transform in step for the day it is.

## What's in the realm

- **Realm roles**: `provider`, `practice_principal`, `practice_manager`,
  `front_desk`, `patient`, `assignor`, `system`.
- **Realm `browserFlow` is `clinician-browser`** — a WebAuthn passkey is
  REQUIRED, with the password form DISABLED and no OTP fallback. That is rule
  15 (REQ-VAULT-04) enforced at the identity layer: practitioner and admin auth
  is passkeys, no password-only paths.

  **It is bound at the REALM, deliberately.** It used to be only an
  `authenticationFlowBindingOverrides` entry on `web`, which left every client
  Keycloak creates for itself — `account-console` above all — falling back to
  the stock `browser` flow. That flow's Username Password Form is REQUIRED, so
  opening the account console asked a passkey-only user for a password that had
  never been set. There was no answer to the prompt. A per-client override only
  covers the clients you remember to think about, and the built-in ones are
  exactly the ones you do not.
- **Public client `web`** (console/portal/tester) — authorization code + PKCE.
  It keeps its explicit override to the same flow: the realm default now covers
  it, but `web` is ours and worth stating rather than inheriting.
- **`patient-carer-browser` flow** (passkey as ALTERNATIVE to password+OTP —
  encouraged, not mandatory) — ready for the patient/assignor portal client
  when M8 auth lands (REQ-CLIENT-02: passkey never a barrier for patients).
- **Confidential service clients** `core-service`, `rules-service`,
  `vault-service` — client-credentials only, used by
  `@aobplatform/auth-client`'s `ServiceTokenProvider` (core already requests
  real tokens for vault calls when `KEYCLOAK_ISSUER`/`KEYCLOAK_CLIENT_SECRET`
  are set).
- **No social/broker identity providers** — deliberately absent given the
  AoB phishing exposure; adding one is a decision, not a default.
- **`loginTheme` and `emailTheme` are both `aobplatform`**, and both are in
  the export. They used to be set only in the running realm, which meant a
  container rebuild re-imported the file, the realm came back looking healthy,
  and the themes were quietly the built-in ones again.
  `npm run validate:realm` now asserts both.

## The login theme

`themes/aobplatform/login/` — mounted into the container by `docker-compose.yml`
alongside the email theme, `parent=keycloak.v2` (the server default this realm
was rendering before, read off the served stylesheet rather than taken from the
docs).

It overrides **one page**: `webauthn-register.ftl`, the "Passkey Registration"
screen. The stock keycloak.v2 markup is reproduced unchanged — same form, same
action, same hidden fields, same `registerByWebAuthn` script, same buttons —
wrapped in two divs with an `<aside>` beside it. Nothing the authentication
flow reads was touched, deliberately: a login theme that throws locks out every
practitioner at once and there is no password path to fall back to (rule 15).

The aside lists the browser and operating-system dialogs that appear after
Register, for Windows, Mac, Android and iPhone/iPad, chosen with a labelled
`<select>` that defaults from the user agent and gates nothing. The Windows
list is the one that matters: step 3 sends the person to "Windows Hello or
external security key" and the note tells them why Microsoft Password Manager
will enrol and then fail (§2 below, and D-2026-09-12-01).

**Every sentence is in `login/messages/messages_en.properties`**, Keycloak's
string table — the template carries none. Two constraints when editing it:
Keycloak runs messages through `MessageFormat`, so a lone `'` is swallowed and
`{ }` are placeholders (Keycloak's own bundle writes `passkey''s` for this
reason); and `aobPasskeyStepCount<Platform>` must match the number of
`aobPasskeyStep<Platform><n>` keys.

`npm run validate:realm` now runs `login-theme.test.mjs` as well, which reads
the properties file and the template and asserts: no lone apostrophe or brace
in any value, no rule-12 word in any value, every step key the counts promise
(and no orphan past them), the stock form/action/hidden fields/script still
intact, and no password input anywhere in the override. The step count is the
one value read as a NUMBER rather than printed, so a bad one would abort the
render — the template parses it defensively and the whole panel sits inside a
`<#attempt>`, because a page that fails to render is a lockout, not a bug.

Verified 12 Sep 2026 with a CDP virtual authenticator: enrolment completed on
the themed page and the credential it created signed in through
`clinician-browser` to an access token. The account console, the `console`
client and the `web` client all render the theme with zero password inputs.
Light and dark both check out, and there is no horizontal scroll at 360px, at
1280px, or at 200% zoom.

## ⚠ A false claim, found and fixed (21 Aug 2026)

The first version of this file said the clinician flow had "passkey REQUIRED
with no password/OTP fallback". **That was inherited from ReferralPlatform's
README and was not true of the actual config.** Reading the executions through
the Keycloak admin API showed:

```
clinician-browser Credential            REQUIRED
  WebAuthn Passwordless Authenticator   ALTERNATIVE   ← either would do
  Password Form                         ALTERNATIVE   ← including this one
```

A password would have authenticated a practitioner — a rule 15 violation. The
login page only *looked* passkey-only because the test user had no password
set. Now enforced in `transform-realm.mjs` and verified:

```
  WebAuthn Passwordless Authenticator   REQUIRED
  Password Form                         DISABLED
```

`npm run validate:realm` asserts this on every CI run, so the claim cannot
quietly become false again. **Lesson: read the config, not the prose.**

## Verified (21 Aug 2026)

- Realm imports and boots; OIDC discovery serves.
- `core-service` obtains a real client-credentials token, and
  `@aobplatform/auth-client`'s `TokenVerifier` verifies it against the realm
  JWKS end to end.
- The console's sign-in redirects with PKCE `S256`; the Keycloak login page
  renders **zero password inputs** and no "forgot password" link.
- A practitioner with no registered passkey **cannot sign in at all** — there
  is no fallback to fall back to.

**Not yet verifiable here:** completing the passkey ceremony needs a real
authenticator (or a CDP virtual authenticator, which the headless browser used
in this build does not expose). The redirect, PKCE exchange, callback handling
and token verification are all proven; the biometric tap itself is not.
Worth doing manually on a real device before the design partner sees it.

## The token says how the session signed in (10 Oct 2026, D-2026-10-10-06)

Revoking a tablet and re-baselining an AOBPRINTER chain ask for a fresh second
factor, and core judges it on the token's `amr` claim. This realm had **no amr
mapper**, so every token said nothing, core read "unknown", and revoke refused
every passkey session. It also told them they had signed in "with a password
and nothing else", which nobody had.

The fix has two halves, and Keycloak needs both:
- **the mapper:** `oidc-amr-mapper` on the `web` and `console` clients;
- **the value:** an authenticator config on each credential step of
  `clinician-browser Credential` naming its RFC 8176 value. The passkey step
  names `hwk`. The disabled password step names `pwd`, so a re-enabled one is
  reported rather than hidden.

`maxAge` is 36000, the realm's session maximum, so the claim lasts the whole
session; freshness is judged on `auth_time` in core, not here.
`realm-export.test.mjs` asserts all of it.

**An existing realm needs the script,** because `--import-realm` only runs on
an empty database:

```bash
node infra/keycloak/backup-keycloak.mjs
node infra/keycloak/apply-amr.mjs
```

It adds what is missing, changes no requirement and binds no flow, and is safe
to re-run. Then sign out of the console and sign in again.

## Passkeys have TWO names, and they never match

This confuses everybody once, so it is written down.

| Where | What it shows | Set by |
|---|---|---|
| Keycloak's enrolment prompt | the label the person types, e.g. `AoBPasskey1` | the person, at enrolment |
| Windows / macOS chooser | the WebAuthn **username**, e.g. `carl@hillsempire.com` | us, when the account is created |

Neither system shows the other's name. Somebody who carefully labels their
credential `AoBPasskey1` is later offered a chooser that says something else
entirely, does not recognise it, and concludes the passkey did not save.

That is why the username is the person's **email address** — it is the one
identifier they will recognise in an operating-system dialog they were not
expecting. It was `admin.<localpart>` first, which recognisably belonged to
nobody.

To check what the server actually holds, rather than guessing from a dialog:

```bash
node infra/keycloak/apply-realm-additions.mjs
```

and for one account, the Admin REST API under
`/admin/realms/aobplatform/users/{id}/credentials` reports the credential type
and its Keycloak label.

## Platform administrators

```bash
node infra/keycloak/invite-platform-admin.mjs --email <address> --name "<full name>"
```

```bash
node infra/keycloak/reset-platform-admin-passkey.mjs --email <address> --reason "<why>"
```

The reset REVOKES every existing passkey before issuing a new enrolment, and
ends live sessions. Lost and stolen are treated identically because the person
reporting it usually cannot tell which it was — a phone left in a taxi is
"lost" until it is not.

Neither command sets a password. There is no password path in this realm for
these clients, and these commands do not create one.

## Which passkey provider captured the enrolment

Windows 11 ships more than one, and the wrong one silently breaks sign-in.

| AAGUID | Provider | Sets UV? |
|---|---|---|
| `08987058-cadc-4b81-b6e1-30de50dcbe96` | Windows Hello Hardware | yes |
| `9ddd1817-af5a-4672-a2b9-3e3dd95000a9` | Windows Hello Software | yes |
| `6028b017-b1d4-4c02-b4b3-afcdafc96bb2` | Windows Hello VBS | yes |
| `d3452668-01fd-4c12-926c-83a4204853aa` | **Microsoft Password Manager** | **no** — see CRITICAL-ISSUES.md §2 |

Microsoft Password Manager prompts for a PIN, which looks exactly like user
verification and is not: it unlocks the manager's own vault. The realm requires
UV, the assertion arrives without it, and sign-in is refused with a message
that explains none of this.

To read the AAGUID on an account's credentials, use the Admin REST API:
`/admin/realms/aobplatform/users/{id}/credentials` — the `credentialData`
field carries it.

## The tier 2 sandbox realm — `aobplatform-tier2`

**A SECOND REALM, not a second application** (Carl asked whether to prototype
tier 2 in a side app; 12 September 2026). Tier 2 is almost entirely Keycloak
configuration, so a standalone prototype would have skipped the only parts with
risk in them: the browser flow itself, how core reads the resulting session,
and whether the passkey users already in the realm carry on working. A second
realm exercises all three against the real application, because the app already
picks its realm from environment variables.

`aobplatform` IS NOT TOUCHED by any of this. `tier2-realm.mjs` compares the
realm name against a constant before it makes a single request, and every admin
call it makes asserts the path it is about to use.

### What is in it

Everything the main realm has, plus tier 2 (`AUTH-TIERS.md` §2/§4/§5,
`DECISIONS.md` D-2026-09-12-11):

- **`practice-browser`**, bound at the realm and on the `web` client. Username,
  then **either** a passkey **or** a password and a one-time code. The code form
  is REQUIRED and is deliberately *not* wrapped in `conditional-user-configured`
  — that wrapper is the difference between "a code" and "a code if you happen
  to have set one up".
- **Two CONDITIONAL subflows on opposite sides of one role check.** A holder of
  `platform_admin` meets `practice-browser Operator`, which REQUIRES a passkey
  and contains no password form; everybody else meets
  `practice-browser Practice`. Written this way because a conditional that
  PASSES does not stop what follows it — one conditional followed by an
  alternative would have asked an operator for a passkey *and then* a password.
- **`operator-browser`** on the `console` client: passkey REQUIRED, password
  form DISABLED, the same shape as `clinician-browser`. Belt and braces with the
  role gate — a per-client binding covers the clients you remember to think
  about, a role gate covers the people.
- **A password policy**: `length(12) and maxLength(128) and notUsername and
  notEmail and passwordHistory(5)`. Length over complexity theatre, deliberately
  — character-class rules push people towards `Passw0rd!` and buy nothing an
  offline attacker cares about. `tier2-realm.test.mjs` asserts none is added.
- **Plain TOTP**, six digits over thirty seconds, a code never reusable. No
  registration with Google or Microsoft, no API key, no fee.
- **An `amr` claim on both public clients.** Keycloak's `oidc-amr-mapper` reads
  the completed executions and each one's `default.reference.value`, so the
  token says `["pwd","otp"]` or `["hwk"]`. `packages/domain/src/auth-method.ts`
  turns that into the product's own words; `apps/core` reads it off the actor.

### Pointing the stack at it, and back

Four variables in `apps/core/.env` and one in `apps/web/.env.local`. Nothing
else changes: the client ids and every redirect URI are identical, which is
what `tier2-realm.test.mjs` asserts.

| Variable | Main realm | Sandbox |
|---|---|---|
| `KEYCLOAK_PUBLIC_ISSUER` (core) | `http://localhost:21024/realms/aobplatform` | `http://localhost:21024/realms/aobplatform-tier2` |
| `KEYCLOAK_JWKS_URI` (core) | `http://127.0.0.1:21024/realms/aobplatform/protocol/openid-connect/certs` | `http://127.0.0.1:21024/realms/aobplatform-tier2/protocol/openid-connect/certs` |
| `KEYCLOAK_ISSUER` (core) | `http://127.0.0.1:21024/realms/aobplatform` | `http://127.0.0.1:21024/realms/aobplatform-tier2` |
| `KEYCLOAK_REALM` (core) | `aobplatform` | `aobplatform-tier2` |
| `NEXT_PUBLIC_KEYCLOAK_ISSUER` (web) | unset — `apps/web/app/auth.ts` defaults to the main realm | `http://localhost:21024/realms/aobplatform-tier2` |

The `localhost` / `127.0.0.1` split is not cosmetic and is the same one the
rest of this file explains: `PUBLIC_ISSUER` is compared to the `iss` claim as a
STRING and must be what the browser used; the other two are fetched by Node,
which resolves `localhost` to `::1` first on Windows and dies in Docker's IPv6
forwarding. Getting it wrong produces `unexpected iss claim value` on every
browser-issued token, and stays invisible until something verifies one.

Restart core and the Next dev server after changing them. To go back, put the
five values back — there is no state anywhere else that remembers which realm
was in use.

### Building it, and proving it

```bash
node infra/keycloak/tier2-realm.mjs          # build (drops and rebuilds if present)
node infra/keycloak/tier2-realm.mjs --keep   # only if absent
node infra/keycloak/tier2-realm.mjs --delete # remove it

node infra/keycloak/tier2-verify.mjs         # password + code, end to end, no browser
node infra/keycloak/tier2-verify-passkey.mjs # passkeys, with a CDP virtual authenticator
```

**It rebuilds rather than patches, and that is the point.** Patching flows in
place is how a script quietly diverges from the file it claims to describe —
the drift that made `transform-realm.mjs` unsafe to re-run (§ at the top of
this file). The sandbox holds nothing precious: its accounts are made by the
two verify scripts, which recreate them.

`tier2-verify.mjs` drives the real HTML forms with a cookie jar and computes
the one-time codes in Node from the secret Keycloak generated during enrolment,
so no phone is involved and the run repeats. `tier2-verify-passkey.mjs` needs a
browser and is separate for that reason.

**`npm run validate:realm` now runs `tier2-realm.test.mjs` too** — a SEPARATE
guard that never reads `realm-export.json`. Its first two checks are that the
file names `aobplatform-tier2` and that it is not the realm anybody signs in to.

### Two things worth knowing before this becomes real

- **An account with no credential at all cannot sign in.** Worth stating
  because the opposite is a plausible Keycloak behaviour: a REQUIRED
  authenticator the user is not configured for can be turned into a required
  action and waved through. It is not, here — the realm answers "Invalid
  username or password" (checked 12 September 2026, and pinned by the first
  check in `tier2-verify.mjs`). Enrolment therefore has to go through the
  action-token invitation, which is what the platform already sends.
- **Required actions run in Keycloak's own priority order, not the order they
  were asked for.** This realm serves the authenticator setup before the
  password. Both happen before the person reaches the application, which is
  what "one pass" means; the order itself is Keycloak's default and nothing
  should be built on it.
